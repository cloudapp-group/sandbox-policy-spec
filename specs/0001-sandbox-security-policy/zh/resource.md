# 规格：资源策略

属于[提案 0001 — 沙箱安全策略](./overview.md)的一部分。关键词 **MUST**、**MUST NOT**、**SHOULD**、**MAY** 按 RFC 2119 解释。

---

## 1. 范围

本规格定义 `SandboxPolicy` 对象的 `resource` 子策略。本模块之所以叫 **resource**，是因为它管的正是这件事：一个沙箱可以消耗什么。它涵盖三份契约：

- **速率上限** —— 沙箱消耗得多**快**：出站请求速率与并发数、磁盘读写吞吐与 IOPS。一个上限是被**整形**的，永不失败：超出的部分被排队并降速（§3.1）。
- **预算** —— 那一样会不可逆累积的东西的窗口化**总量**：LLM Token，按 `minute`、`hour`、`day`、`week`、`month` 窗口，或按沙箱的整个 `lifetime`。
- **治理** —— 预算耗尽时会发生什么：告警、暂停、终止，或**挂起等待人工介入**，外加通知，使人能及时知情。

速率与总量之分决定了 `onExceeded` 落在哪里。一个上限不可能被超出 —— 它是一个速度，高于它的流量会等待 —— 所以它没有动作、没有事件、也没有挂起状态。一份预算会被耗尽，而耗尽时必须发生某件事。Token 是这里唯一的预算，这就是 `onExceeded` 只出现在 `tokens` 之下的原因（§6）。那是结构的必然结果，而不是一条需要记住的规则。

同一个划分也是本模块与 `network` 之间的接缝：`network` 决定*什么可以被访问*，`resource` 决定*可以流动多少*。请求速率上限属于消耗，所以它是这里的一个速率，而不是出站规则上的一个字段（[overview.md](./overview.md) §11.9）。

**本模块有意不再涵盖的内容。** 早先的版本带有 `quota.cpuMillicores`、`quota.memoryMiB`、`limits.cpuSeconds`、`limits.netEgressBytes` 与 `limits.diskWriteBytes`。它们全部被移除。约束 CPU 与内存是每一个编排系统与 VMM 都已经在做的标准运维动作 —— 一个 Kubernetes 的 `resources.limits` 块、一个 Cloud Hypervisor 的 `--cpus` / `--memory` 参数 —— 在这里重述一遍，只会让策略对象看起来拥有一个它其实只是复述的决定。字节总量被删是另一个理由：累积字节数对它本想代表的那种危害是个糟糕的代理。真正会拖垮共享基质的是*速率*，真正会花钱的是 Token。剩下的，是通用运维工具**不**约束的那部分消耗面。

代价被写出来，而不是留给人去发现。`limits.cpuSeconds` 曾是本提案针对失控循环的唯一强制手段（[overview.md](./overview.md) §2.3）。对这一威胁的收容，现在依靠空闲超时生命周期与 Token 预算，而对一个 Agent 循环来说，Token 预算在实践中才是那个起约束作用的量：一个会调用模型的循环烧 Token，而一个不调用模型的循环烧的 CPU 已经被编排系统自己的配额封住了。真正失去的是介于两者之间的那种情况 —— 一个沙箱在自己的 CPU 配额之内，什么都不调用，只在本地算力上空转数小时。那现在是一个运维侧的关切，而本对象不再声称相反。

不在范围内：计费与定价（下面的用量暴露是计费所依赖的契约）；空闲超时与生命周期（既有行为，不变 —— 只是它对被挂起的沙箱仍然适用，§7）。

## 2. 对象模型

```yaml
policy:
  resource:
    rate:                                  # 上限：被整形，永不超出（§3.1）
      network:
        requestsPerSecond:     int         # 出站请求数/秒
        maxConcurrentRequests: int         # 在途出站请求数
      disk:
        readBytesPerSec:       int
        writeBytesPerSec:      int
        readIops:              int
        writeIops:             int
    limits:
      tokens:
        onExceeded: warn | pause | hold | kill   # 下面三个维度的缺省动作
        input:                             # prompt token
          windows:  {minute?, hour?, day?, week?, month?, lifetime?}
          onExceeded?: action
        output:                            # completion token
          windows:  {minute?, hour?, day?, week?, month?, lifetime?}
          onExceeded?: action
        total:                             # input + output
          windows:  {minute?, hour?, day?, week?, month?, lifetime?}
          onExceeded?: action
    notifications:
      thresholds:      [number]            # 各限额的比例；默认 [0.8, 1.0]
      webhook:         URL                 # 可选的投递端点
```

预算维度：`tokens.input`、`tokens.output`、`tokens.total`。三者互相独立：每个被配置的维度都在自己的计数器上被强制执行。

## 3. 字段规格

| 字段 | 类型 | 约束 | 默认 | 语义 |
| --- | --- | --- | --- | --- |
| `rate.network.requestsPerSecond` | `int?` | > 0 | 缺省 = 无限 | 每秒出站请求数上限（§3.1、§5.1）。 |
| `rate.network.maxConcurrentRequests` | `int?` | > 0 | 缺省 = 无限 | 同时在途的出站请求数上限。 |
| `rate.disk.readBytesPerSec` | `int?` | > 0 | 缺省 = 无限 | 沙箱块设备上的读吞吐上限。 |
| `rate.disk.writeBytesPerSec` | `int?` | > 0 | 缺省 = 无限 | 写吞吐上限。 |
| `rate.disk.readIops` | `int?` | > 0 | 缺省 = 无限 | 每秒读操作数上限。 |
| `rate.disk.writeIops` | `int?` | > 0 | 缺省 = 无限 | 每秒写操作数上限。 |
| `limits.tokens.<dimension>.windows` | `map?` | 键取自 `{minute, hour, day, week, month, lifetime}`；值 > 0。**可以**设置多个窗口，它们各自独立地被强制执行。 | 缺省（无限额） | 每窗口的最大 Token 消耗量（§4）。 |
| `limits.tokens.<dimension>.onExceeded` | `enum?` | `warn` \| `pause` \| `hold` \| `kill` | `limits.tokens.onExceeded` | 该维度任一窗口被耗尽时的动作。 |
| `limits.tokens.onExceeded` | `enum?` | 同上 | `hold` | 三个 Token 维度的缺省动作。 |
| `notifications.thresholds` | `[number]?` | 每个取值落在 (0, 1] 内。升序排列。 | `[0.8, 1.0]` | 在各已配置限额的这些比例处发出通知。 |
| `notifications.webhook` | `string?` | `https` URL | 缺省 | 接收通知事件的端点（§8）。 |

零或负的速率与限额、空的 `windows` 映射、以及落在 (0, 1] 之外的阈值，**必须**以 `400 INVALID_POLICY` 拒绝。

`lifetime` 是那个永不重置的窗口：一份覆盖沙箱整个存在期的预算。五个周期性窗口在各自的边界处重置（§4.1）。

### 3.1 速率上限语义

`rate` 之下的每一个字段都是一个上限，而上限与预算的行为方式不同，这一点需要在这里一次性定下来，而不是逐字段说明：它们没有超出转换，因为它们不可能被超出。

1. 高于上限的工作**必须**被**整形** —— 排队并降速到上限 —— 而不是被拒绝。任何 `rate` 字段都没有 `onExceeded` 动作、没有 `resource.exhausted` 事件、也没有挂起状态。一个处于上限的沙箱是个慢沙箱，不是个失败的沙箱。
2. **一个上限被定义为某个区间上的平均值，且该区间必须被写明。** 一个部署**必须**在任意 1 秒或更长的窗口上按平均值满足每个已配置的上限，且对一个持续请求量不低于上限的工作负载，**不得**交付低于所配置速率 90% 的实际速率。瞬时突发高于上限**可以**发生，且不构成违反。

   这一条存在，是因为常见的实现是一个带补充周期与停顿区间的令牌桶，而这样的桶在补充周期相对停顿区间很短时，可以只交付其名义速率的一小部分。一个配置为 1000 IOPS 的值，可以从一份看起来站得住脚的配置里变成实际 100 IOPS。若没有写明的平均区间，两个部署会把同一个字段解析成相差一个数量级的速率，而**两者都会声明它 `enforced`**（[overview.md](./overview.md) §8.2）—— 那正是那一节存在所要防止的失败。
3. 缺省意为无限：沙箱只受平台自身容量的约束。零**必须**以 `400 INVALID_POLICY` 拒绝 —— 一个可以访问某个目标（`network`）却不能向它发出一个请求的沙箱，其失败模式与一个坏掉的网络无从区分，而原则 4 的存在正是为了防止这个。「什么都不要发」在 `network` 里表达，那里的拒绝是可解释的。
4. **整形必须可观测。** 每一个曾延迟过工作的上限，**必须**逐字段地通过用量暴露报告它所造成的累积延迟（§9.3）。整形不产生事件、也不产生失败，这意味着一个不可观测的上限会把「我的沙箱很慢」变成一个没人能从平台自己的记录里回答的问题。原则 4 要求一次拒绝必须可解释；把同一套论证用在上限上，就要求一次变慢必须可归因，而可归因意味着指名那个字段。
5. 入站整形不在本规格中。入站流量不是沙箱要控制的自身消耗，而一个工作负载无法影响的上限不是一个策略字段（§13.11）。
6. 上限与预算相互独立，且**必须**能同时被强制执行。请求速率上限降低一个 Token 窗口被填满的速度；它绝不替代那个窗口。

## 4. 窗口语义

### 4.1 窗口定义与对齐

所有窗口都是固定的，且对齐到 UTC：

| 窗口 | 周期 | 重置时刻 |
| --- | --- | --- |
| `minute` | 60 秒 | 每个 UTC 分钟的开始 |
| `hour` | 3600 秒 | 每个 UTC 小时的开始 |
| `day` | 24 小时 | 每天 UTC 00:00 |
| `week` | 7 天 | 每周一 UTC 00:00（ISO-8601） |
| `month` | 日历月 | 每个 UTC 月首日的 00:00 |
| `lifetime` | — | 永不重置 |

### 4.2 计数器

1. 每一个（沙箱、维度）对都有一条只追加的用量流；一个窗口的计数器是当前窗口周期内用量之和；`lifetime` 计数器是自沙箱创建以来的总量。
2. 一个窗口计数器在其窗口内**必须**非递减，并在翻转时重置为零。lifetime 计数器**必须**单调非递减。
3. 计数器跨 pause/resume 保持；resume 从不重置用量。
4. 快照恢复 / 克隆：被恢复的沙箱继承来源的**策略**（限额、上限、动作、通知）；所有计数器，包括 lifetime，从恢复点起从零开始。（运维方是否可以改选继承计数器，是一个开放问题，§13。）

### 4.3 强制执行

1. 每个已配置的窗口都独立地被强制执行：当任一窗口的计数器首次达到其限额时，该维度的动作（§6）被触发。
2. 同一维度的多个窗口共用该维度的 `onExceeded`。
3. 若在同一次观测中有若干维度或窗口被耗尽，其中最严厉的动作胜出：`kill` > `hold` > `pause` > `warn`。
4. 检查**应该**既周期性运行、也在每个计量边界处运行，使分钟粒度的限额能及时生效。两次检查之间的过冲**必须**被吸收：动作在第一次观测到达到或超过限额时触发，且上报的用量**可以**超出限额，超出幅度不超过观测粒度。
5. 周期性耗尽由翻转重新武装：一个在 10:07:30 耗尽其 `minute` 窗口、并在 10:08:00 翻入一个新窗口的维度，可以再次消耗，而新窗口中的一次新耗尽是一次新的转换，带有它自己的事件。

## 5. 计量语义

### 5.1 测量点

| 面 | 在何处测量 |
| --- | --- |
| `rate.network.*` | 平台的出站请求路径 —— 与 `network` 七层规则所用的同一个七层强制点（[network.md](./network.md) §2.4）。一个*请求*是一个 HTTP 请求；连接复用不会把若干请求变成一个。 |
| `rate.disk.*` | 沙箱的块层，按每个方向分别计，计的是下发到设备的操作。 |
| `tokens.*` | LLM API Token，依 §5.2。 |

`rate.network.*` 有意计的是请求而不是连接。单条 keep-alive 连接可以承载无界数量的请求，所以一个连接上限约束不了这些字段所要约束的东西。其后果是一项真实的依赖，且没有被抹平：出站路径上没有七层强制点的部署根本无法计量请求，且**必须**把两个 `rate.network` 字段都声明为 `unsupported`（[overview.md](./overview.md) §8.2）。是否应该为这类部署提供一个连接级上限作为兜底，是一个开放问题（§13.14）。

### 5.2 LLM Token 真值来源

明确的优先级，因为 Token 用量只能从 API 事务本身得知：

1. **响应侧记账（首选）。** 当一个沙箱发往 LLM API 的请求流经平台的出站 HTTP/HTTPS 路径时，响应的 `usage` 字段对该请求的 Token 计数具有权威性。
2. **显式上报（兜底）。** SDK 上的 `sandbox.report_usage()` 让调用方能上报响应侧记账观测不到的用量（非 HTTP 提供方、省略 `usage` 的提供方）。它**必须**以一个有权管理该沙箱的主体身份被认证，条件与审批 API（§7.4）相同 —— 不受信的沙箱内代码**不得**能够写自己的计数器。

### 5.3 流式、重试与部分消耗

实践中大多数 Token 支出通过可能被重试或被中途切断的流式响应到达。把这些情形留给实现，等于保证日后出现一场计费争议，所以记账方式在此定下。

| 情形 | 规则 |
| --- | --- |
| 非流式响应 | 响应的 `usage` 具权威性；在完成时计量一次。 |
| 正常完成的流式响应 | 在流终止时计量；**最后一个 chunk** 的 `usage` 载荷具权威性。 |
| **没有** `usage` 载荷就终止的流式响应 —— 客户端中断、沙箱超时、传输错误、提供方省略 | 用量仍然**必须**被计量，来自一个从线上实际观测到的内容导出的**估计**。计量**不得**被跳过：跳过它会让「在最后一个 chunk 之前中断」变成一条免费 Token 的绕过路径。 |
| 重试，无论是沙箱重试还是平台重试 | 每一次向提供方的尝试都**独立**计量，因为提供方按尝试计费。 |
| 未产生任何 Token 的尝试 —— 连接失败，或在任何内容之前就出现 HTTP 错误 | 计量为零。 |
| 请求进行中沙箱被 kill 或 pause | 依上述规则计量。结束一个沙箱不会抹掉已经产生的消耗。 |

1. 一个估计**必须**是实际用量的**下界**：它只计已观测到的部分，绝不加上投机性的加成。这使 §5.4 的修正保持为可加的，也使平台不会为自己的不确定性多收费。
2. 平台内部的重试**必须**归属于引发它们的那个沙箱。
3. 这些规则管的是*计量*。一个被计量的量是否*可计费*，是定价问题，不在范围内（§1）。

### 5.4 来源标记与修正

1. 每一个被计量的量都携带一个 `provenance` 标记：`response`（一个权威的 `usage` 载荷）、`estimated`（§5.3），或 `reported`（§5.2.2）。
2. 来源标记**必须**通过用量（§9）暴露，使平台能对被估计的量与权威的量分别计费、告警或对账。
3. 若某个请求的权威 `usage` 载荷在一个估计已被计量之后才到达，其差值**必须**作为一个额外的**正**增量施加。**不得**施加负向修正，因为窗口与 lifetime 计数器是非递减的（§4.2.2）—— §5.3.1 的下界要求正是让这一点成立而非仅仅方便的原因。
4. 计数器**不得**由沙箱内部的不受信代码递增。

## 6. 超限动作

| 动作 | 语义 |
| --- | --- |
| `warn` | 只发出耗尽事件。用于可观测性试点，而非保护。 |
| `pause` | 挂起沙箱。一旦每个触发窗口都已翻转，它变为可恢复，且**应该**在那时自动恢复；一次提高限额的策略更新也会释放它。因此分钟/小时窗口起节流作用，月/生命周期窗口起断路器作用。 |
| `hold` | 挂起沙箱并等待人工决定（§7）。**不**在窗口翻转时自动释放。 |
| `kill` | 立即终止；终态记录导致它的维度与窗口。 |

动作解析：若设置了 `limits.tokens.<dimension>.onExceeded` 则用它，否则用 `limits.tokens.onExceeded`。

`onExceeded` 只适用于 Token 预算，别的都不适用。不存在模块级的缺省值，因为没有别的东西需要它来缺省：`rate` 字段被整形且没有动作（§3.1.1），所以一个坐在模块顶端的动作只会作用于恰好一棵子树，却看起来作用于全部。日后添加第二个预算维度的部署，将需要决定这个动作是否上移；在那之前它待在它有意义的地方。

默认是 `hold`：配置一个限额就是在选择接受治理，而 hold 是唯一一个既安全（消耗停止）又可逆（无数据损失）、同时把最终决定权留给人的动作。没有 on-call 流程的部署**应该**显式设置 `warn` 或 `pause` —— 被挂起的沙箱仍受标准空闲超时生命周期约束，所以一次无人处理的挂起不会永远漏着资源。

`onExceeded` 是本模块唯一的响应字段：依 [overview.md](./overview.md) §8.1.6，**这里没有 `onViolation`**。两者不是恰好落在不同模块里的备选项 —— 它们回答不同的问题，而 §8.1.1 固定了哪个是哪个。一次耗尽意味着工作负载留在了它被给的每一条边界之内、把预算用完了；一次违规意味着它越过了某一条。这就是这套动作集有 `warn` 与 `hold`、而 `onViolation` 两者都没有的原因：对于「需要更多预算」这件事，有可供人决定的东西，而一句关于超支的告警不会让任何保护失效，因为预算从来就不是一种针对意图的保护。

两套动作唯一共有的是 `kill`，且即使是它，作用范围也不同。这里它终止的是**沙箱**，因为消耗是一个沙箱级的量，没有唯一的有罪进程 —— 与 `network` 出于另一个理由被迫采用的粒度相同（[overview.md](./overview.md) §8.1.3）。

`policy.tier`（[overview.md](./overview.md) §7.1）不改变本模块中的任何东西。每个分级都解析为无上限、无窗口限额、以及 `onExceeded: hold` —— 最后这一项已经是上面的默认值。这被写出来而不是省略，是因为一个看着四个模块在 `tier: restricted` 下收紧的读者，有权知道第五个刻意没有：消耗预算是与工作负载相关的具体数字，而不存在一个「受限的那个」`tokens.total` 取值。一个去猜的分级会是一个为了它其实无法改善的安全姿态而破坏工作负载的分级。

### 6.1 影子评估支持

依 [overview.md](./overview.md) §7.2.5，本模块陈述它的立场：**它没有影子评估，因为它没有可影子的东西。**

理由就是上面那一段。影子评估把一个被强制的分级与一个更严的分级作比较，而这里没有任何分级改变任何字段。不存在一组更严的限额供 `auditTier: restricted` 去比对，所以 `auditTier` 指名本模块解析为无发现 —— 不是因为机制缺失，而是因为那个比较是空的。

这不是一个日后靠加上影子支持来补的缺口。如果有一天值得回答「一份更紧的预算本会挡下什么？」，答案已经存在且更好：`onExceeded: warn`（§6）就是那个特性，只是从另一个方向到达的。一个想观察某个候选限额的部署把限额连同 `warn` 一起设上，就能拿到带真实计数器的耗尽事件，而不是对一个还没人选定的数字做一次并行求值。一个结果配两套机制，正是 §10.1 已经为授权拒绝过的事，其论证原样成立。

值得理清的区别：本提案别处的一条影子发现意味着「这次操作本会被拒绝」。这里对应的问题是「这份预算本会被耗尽」，那是关于一个计数器达到某个值，而不是关于对一次操作的决定 —— 而计数器正是本模块真实暴露（§9）而非影子暴露的东西。

## 7. 人工介入（hold）

1. 在一次 `hold` 动作上，沙箱进入**held** 状态：执行被挂起（等价于 pause），且**必须**立即发出一个 `resource.hold_requested` 通知（与 `notifications.thresholds` 无关）。
2. 被挂起的沙箱不自动释放。释放只通过审批 API 或一次策略更新发生。
3. 审批 API：

   ```yaml
   # POST /sandboxes/{sandboxID}/resource/approval
   dimension:  tokens.total      # 可选；缺省表示对该沙箱当前全部 hold 做出决定
   window:     month             # 可选；与 dimension 一起缺省 → 该维度的全部 hold
   decision:   approve           # approve | deny
   allowance:  1000000           # 仅 approve，可选：为当前窗口周期追加的额度
   raiseLimit: 60000000          # 仅 approve，可选：对该沙箱持久提升限额
   ```

   - `approve` 恢复沙箱。`allowance` 只加到当前窗口周期的额度上（翻转时回退）；`raiseLimit` 持久更新该沙箱的生效限额。
   - 对一个 `lifetime` 窗口，额度永不回退（lifetime 没有翻转）：它是对沙箱剩余存在期的一次永久追加。
   - `deny` 终止沙箱。
4. 授权：审批**必须**由一个有权管理该沙箱的已认证主体（所有者/运维方）通过控制面 API 执行。审批 API **不得**可从沙箱内部调用，也**不得**能用沙箱作用域的凭据调用 —— 不受信的 Agent 代码不能批准它自己的挂起。
5. 每一次审批**必须**被审计：审批者身份、目标、决定，以及任何额度/提升。
6. 被挂起的沙箱仍受标准空闲超时生命周期约束（空闲时 kill/pause），所以被遗弃的挂起最终会被回收。

## 8. 通知

1. **阈值通知。** 当任一（维度、窗口）计数器越过其限额的某个已配置阈值比例时，**必须**发出一个 `resource.notification` 事件，每个窗口周期内每个阈值至多一次：`{sandboxID, dimension, window, used, limit, threshold, at}`。
2. **耗尽事件。** 每一次耗尽转换**必须**发出 `resource.exhausted`：`{sandboxID, dimension, window, used, limit, action}`。
3. **挂起事件。** 每次挂起发出 `resource.hold_requested`（§7）；`resource.approved` / `resource.denied` 记录决定与审批者。
4. **投递。** 当配置了 `notifications.webhook` 时，事件**必须**以 HTTPS POST 携带上述 JSON 载荷投递，至少一次，带有界的重试。Webhook 认证/签名是一个开放问题（§13）。无论是否配置 webhook，事件**必须**也可通过平台的事件流获得。
5. 通知载荷**不得**包含除计数器本身之外的沙箱数据。
6. 整形不发出事件（§3.1.1）。它改为通过用量报告（§9.3），因为一个延迟过工作的上限没有什么可供接收方去处理 —— 只有可供运维方去查阅的东西。

## 9. 用量暴露

1. `GET /sandboxes/{sandboxID}` **必须**包含一个 `resource` 对象：

   ```yaml
   resource:
     rate:
       network: { requestsPerSecond: 50, maxConcurrentRequests: 16 }
       disk:    { writeBytesPerSec: 52428800, writeIops: 2000 }
     shaped:
       requestsPerSecond: { delayedSec: 12.4, delayedOps: 318 }
       writeBytesPerSec:  { delayedSec: 3.1,  delayedOps: 20481 }
     usage:
       tokens:
         total:
           current:    { minute: 3500, day: 155000, lifetime: 1200000 }
           limits:     { minute: 10000, day: 1000000, month: 50000000 }
           provenance: { response: 1150000, estimated: 40000, reported: 10000 }
     state: { held: false, exhausted: [] }
   ```

2. `limits` 报告生效的已配置窗口；`current` 报告那些已配置窗口的窗口内计数器。即使没有配置 lifetime 限额，lifetime 计数器也**必须**被报告（计费需要它们）。
3. `rate` 报告已设置的上限，省略无限的那些。上限没有 `usage` 条目 —— 一个速率没有计数器（§3.1）—— 取而代之，它们伴随 `shaped`，后者以造成延迟的那个上限字段为键。`delayedSec` 是工作在那个上限上等待的生命周期累积时间，**必须**单调非递减；`delayedOps` 是曾等待过的请求数或 I/O 操作数。一个从未延迟过任何东西的上限**可以**从 `shaped` 中省略。指名那个字段才是要点：正是它把「沙箱很慢」变成「沙箱正处于它的写入上限」（§3.1.4）。
4. 对 Token 维度，`provenance` 报告这些量是如何得知的生命周期拆分（§5.4）。三个值**必须**加总等于 lifetime 计数器，使租户能看到一份账单有多少建立在估计之上。
5. `state.exhausted` 列出当前被耗尽的（维度、窗口）对；`state.held` 在有挂起待处理时为真。
6. SDK 以 `sandbox.resource` 暴露同一个对象。

## 10. 合并语义

在 [overview.md](./overview.md) §5 之上：

| 字段 | 合并细化 |
| --- | --- |
| `rate.*` | 逐字段取已设置值中的最小值。什么都不设的来源保留低优先级的值。高优先级来源不能*提高*低优先级来源设定的上限，也不能取消它。 |
| `limits.tokens.*.windows` | 按（维度、窗口）：取已设置值中的最小值；无任何来源设置的维度为无限。高优先级来源不能*移除*低优先级来源设定的限额。 |
| `onExceeded`（维度缺省与逐维度） | 最严厉者胜出：`kill` > `hold` > `pause` > `warn`。 |
| `notifications.thresholds` | 跨来源取并集、去重、升序排列。 |
| `notifications.webhook` | 跨来源取并集（可观测性是可叠加的）。 |

**本模块现在没有合并例外。** 上一版有一个：`quota.cpuMillicores` 与 `quota.memoryMiB` 保留覆盖语义而不是只能收窄，因为那是既有的模板行为、改它会破坏调用方（[overview.md](./overview.md) §9）。移除那些字段（§1）连带移除了那个例外，于是这里每一个字段都是只能收窄的，共享的合并原则无需附加条件即成立 —— 这值得记下来，因为 overview.md 的 §5 少一条成文例外就更容易推理。

### 10.1 可授权字段

依 [overview.md](./overview.md) §5.1.8，每个模块都声明它的可授权面。**本模块没有。** 任何 `resource` 字段都不可以被一次限时授权放宽。

临时的额外消耗在这里已经是一等操作，而它与授权形状不同：审批 API（§7.3）由一次**挂起**驱动，所以人是在沙箱确实需要更多的那个时刻、把被耗尽的计数器摆在面前时做决定的。而授权是在需求被证实之前发出的预先批准。给本模块加上授权，会让同一个结果有两套机制，其中一套丢掉了另一套所依赖的信息。

`rate` 字段也不可授权，而对它们理由更简单：授权在一段有界的时间里放宽一条限制，而一个被临时提高的上限只是另一个上限。没有任何东西正在被拒绝，所以没有什么可放宽。

> **术语。** 审批 API（§7.3）的 `allowance` 字段有意*不*叫授权。它向一个窗口计数器追加额度、且自身没有 TTL —— 它在窗口翻转时回退，对 `lifetime` 则永不回退 —— 这使它与 [overview.md](./overview.md) §5.1 的限时授权是不同的机制。两者曾短暂地都叫 `grant`；这个字段被改了名，而不是留一个词在同一个对象里表示两件事。

## 11. 错误

| 代码 | 出现面 | 载荷 | 何时 |
| --- | --- | --- | --- |
| `INVALID_POLICY` | 400 | `{field, reason}` | 非正的速率或限额、非法窗口键、落在 (0, 1] 之外的阈值。 |
| `POLICY_RESOURCE_EXHAUSTED` | 终态 / 事件 | `{dimension, window, used, limit, action}` | 动作为 `kill` 的耗尽（或一次审批 `deny`）。 |

| `POLICY_UNSUPPORTED` | 400 | `{field, capabilityVersion}` | 在 `enforcement: strict` 之下指名了一个本部署声明为 `unsupported` 的 `rate` 字段（[overview.md](./overview.md) §8.2）。 |
| 审批类错误 | 400 / 409 | `{reason}` | 审批指向的不是当前任何挂起，或额度/提升非法。 |

不存在针对达到上限的错误，因为达到上限不是一次失败（§3.1.1）。

## 12. 验收标准

1. 多窗口强制执行：`tokens.total` 按 `minute` 限额（动作 `pause`）且按 `month` 限额（动作 `hold`）时，一次超过分钟限额的突发暂停沙箱，它在分钟翻转时变为可恢复（并自动恢复）；越过月限额则把它挂起等待审批。
2. 翻转重新武装：分钟窗口重置后，直到新的阈值/耗尽转换出现之前，达到新限额之内的消耗不产生事件。
3. 挂起需要人：被挂起的沙箱不在窗口翻转时恢复；`approve`（带或不带额度/提升）恢复它；`deny` 终止它；额度为 N 时在当前周期内至多再允许 N 个单位。
4. 审批 API 拒绝以沙箱作用域凭据认证的调用。
5. 阈值通知在每个窗口周期内每个阈值至多触发一次；耗尽与挂起事件在每次转换时触发。
6. lifetime 计数器单调，且即使没有 lifetime 限额也被报告。
7. 同时耗尽解析为最严厉的动作。
8. 恢复/克隆：策略被继承，所有计数器为零。
9. 合并后的逐窗口限额与合并后的上限都取最小值；合并后的动作取最严厉。
10. **流式。** 一个正常完成的流以来源标记 `response` 计量最后一个 chunk 的 `usage`。同一个流在其最后一个 chunk 之前被中断，仍以来源标记 `estimated` 计量一个非零量，且该量不大于完成的那个流所计量的量。
11. **重试。** 三次各自返回 `usage` 的提供方尝试计量三次；在任何内容之前失败的一次尝试计量为零。平台发起的重试归属于发起方沙箱。
12. **迟到的修正。** 在一个估计之后到达的权威 `usage` 只施加正增量；任何计数器都不曾减少。
13. **来源标记暴露。** `response` / `estimated` / `reported` 拆分被报告，且加总等于 lifetime 计数器。
14. 以沙箱作用域凭据调用 `report_usage` 被拒绝。
15. **上限整形而不失败。** 逐个设置每个 `rate` 字段，一个请求量超过上限的工作负载以大致等于所配置速率的速度完成；没有请求被拒绝、没有 I/O 返回错误、没有 `resource.exhausted` 事件发出，且沙箱从未被该上限暂停、挂起或终止。字段不设置时，同一工作负载不被限速。
16. **上限精度。** 对每个 `rate` 字段，一个持续 10 秒请求量不低于上限的工作负载，在该时段内任意 1 秒区间上的平均值达到所配置速率的 90% 至 100%（§3.1.2）。令牌桶交付明显更少的部署不通过本标准，且**不得**把该字段声明为 `enforced`。
17. **请求计数。** 在 `requestsPerSecond: N` 之下，通过**单条** keep-alive 连接发出的 N+1 个 HTTP 请求被当作 N+1 个请求整形，而不是当作一条连接（§5.1）。
18. **整形可归因。** 经过一段整形之后，`resource.shaped` 指名那个延迟了工作的上限字段，带一个非零且单调的 `delayedSec`。从未延迟过任何东西的上限什么都不报告。
19. **上限与预算相互独立。** 一个同时设置了 `rate.network.requestsPerSecond` 与一个 `tokens.total` 窗口的沙箱，在预算被达到时仍触发该窗口的动作；整形只是延后那件事发生的时刻。
20. **不受支持的速率字段。** 在 `enforcement: strict` 之下，指名一个部署声明为 `unsupported` 的 `rate` 字段以 `400 POLICY_UNSUPPORTED` 被拒绝；在 `bestEffort` 之下它被接受并被报告为惰性。

## 13. 开放问题

1. **时区。** 窗口对齐到 UTC。部署是否应该能把 `day`/`week`/`month` 对齐到某个本地时区？
2. **滑动窗口。** 固定窗口简单，但允许在边界处出现 2 倍突发（一个窗口末尾用满配额，紧接下一个窗口开头再用满）。是否需要滑动窗口，还是这对 v1 可以接受？
3. **自动恢复。** `pause` 是否应该在翻转时自动恢复（现提议为 SHOULD），还是要求一次显式恢复？
4. **Webhook 认证。** HMAC 签名方案？共享密钥存在哪里？
5. **审批 RBAC。** 哪些主体可以审批：仅沙箱所有者、命名空间运维方，还是任何拥有集群管理员权限的人？
6. **额度可见性。** 已批准的额度是否应该出现在 `resource.usage` 里，使平台能为已批准的超额计费、且运维方能看到当前窗口有多少是额度而不是预算？曾经放在这里的命名冲突已解决：这个字段是 `allowance`，而 `grant` 只表示 [overview.md](./overview.md) §5.1 的限时策略放宽。
7. **逐窗口动作。** `onExceeded` 是否应该可以按窗口设置而不是按维度设置（例如同一维度上 `minute`→`pause`、`month`→`hold`）？
8. **恢复/克隆时的计数器继承。** 这里提议的是重置；继承是否应该作为一个运维方可选项？
9. **估计方法。** §5.3 固定了一个估计的*性质*（下界、从已观测内容导出）而非算法。算法及其预期误差是否应该被公布，使租户能审计其用量中被估计的那部分？
10. **缓存与推理 Token。** 提供方越来越多地把缓存读取与推理 Token 分开计量。那些是否成为它们自己的维度，还是折入 `input` / `output`？
11. **入站整形。** §3.1.5 只规定了出站。对于服务公共流量（`network.ingress`）的沙箱，是否应该存在一个入站上限；若有，考虑到沙箱并不选择有多少流量到达，它究竟算不算一个 `resource` 字段？
12. **磁盘占用，以及基质无法归属的写入。** 从字节总量转向速率之后仍留下两处缺口。没有任何东西约束磁盘上的总占用 —— 一个沙箱可以慢慢填满一个卷、同时停在每个上限之下 —— 所以一个容量限额可能仍然需要，而它会是一个总量而不是一个速率，那将是唯一一处非 Token 预算重新出现的地方。另外，`rate.disk.*` 只在基质把 I/O 归属到沙箱的地方可强制执行；§14 记录了它在哪里做不到。规范是否应该要求部署陈明它的磁盘上限覆盖*哪些*可写区域，就像 [filesystem.md](./filesystem.md) 要求路径规则必须被枚举那样？
13. **逐目标速率。** 请求速率上限是按沙箱的。一个速率能否附着到单条出站规则上，是本问题的镜像，追踪在 [network.md](./network.md) §10.5；它必须被回答一次，而不是两次。
14. **没有七层强制点时的并发。** `rate.network.*` 计的是请求，所以出站路径上没有代理的部署把两个字段都声明为 `unsupported`（§5.1），从而根本没有并发上限。一个连接级上限在那里仅凭 conntrack 就可强制执行。是否应该存在这样一个成文的兜底，同时接受连接与请求是不同的量、且一个 keep-alive 工作负载会从它旁边溜过去？

## 14. 非规范性注记

- Token 计数器来自出站 HTTP 路径；磁盘与请求计数器来自基质自身的记账。本规格只固定上述语义。
- 整形是这里唯一一份被强制执行而非被计量的契约：平台给沙箱降速，而不是给它计数。§9.3 的 `shaped` 计数器存在，是为了让这种降速仍然可见，这也是 §3.1.4 把它们定为规范性要求、而不是把可观测性留给各部署的原因。
- **基质映射。** 两个基质都通过单一接口暴露字节速率与操作速率限制，所以 `readIops` / `writeIops` 相对 `readBytesPerSec` / `writeBytesPerSec` 不给部署带来任何额外成本。在容器基质上那个接口是 cgroup v2 的 IO 控制器，其 `rbps` / `wbps` / `riops` / `wiops` 键在达到限额时**延迟** I/O —— 那就是 §3.1.1 的整形语义本身，而不是它的近似。在 VM 基质上则是 VMM 的逐磁盘速率限制器，带独立的带宽桶与操作桶。VM 这一侧有一个值得指出的性质，因为它把本提案其余部分的模式反了过来：限制器跑在 VMM 里、位于客户机*之外*，所以不同于 `process` 与 `filesystem` 在该基质上的情形（[overview.md](./overview.md) §12.2），这些字段不带信任前提 —— 一个在客户机内持有 root 的工作负载无法解除它们。

  在把其中任何一个声明为 `enforced` 之前有三件事要核对：

  | 字段 | 要核对什么 |
  | --- | --- |
  | `rate.disk.write*` | 缓冲写只在文件系统实现了 cgroup writeback 的地方才被归属到某个 cgroup。在没有实现的地方，writeback I/O 被归属到根 cgroup，从而完全逃出上限。一个容器写入联合文件系统的上层就是这种情形的常见形态，所以其沙箱写在那里的部署声明 `partial`，并在 `knownLimitations` 中记录哪些可写区域*确实*被覆盖 —— 依 [overview.md](./overview.md) §8.2.1 规则 3，「你的一部分写入被降速了」在不知道是哪一部分时是不可用的。一个位于支持 cgroup writeback 的文件系统之上的专用卷，才是这个字段完全可强制执行的配置。 |
  | `rate.disk.read*` | 页缓存命中不向设备下发 I/O，所以读上限只约束未命中缓存的读。一个反复读取热文件的工作负载在两个基质上都是无界的。这是固有性质而不是任何实现的缺口，也使读这一对成为多数部署会声明 `partial` 的那一对。 |
  | `rate.network.*` | 这些来自出站请求路径而不是内核，所以它们需要与 `network` 七层规则、Token 计量同一个七层强制点。没有它的部署把它们声明为 `unsupported`（§5.1）。三个面，一套机制 —— 这是本提案中把那个代理当作核心而非可选基础设施的最强论据。 |
- `rate.network.*` 附着在沙箱的出站路径上，磁盘上限附着在它的块设备上。在容器基质上沙箱是一个 Pod（[network.md](./network.md) §4.9），所以两者都属于该沙箱且不属于别的任何东西 —— 与 VM 基质相同的安排。因此本模块不需要它自己的作用域附注：出站路径、那些设备、计数器所依赖的那个 cgroup，以及策略的主体，全都是同一个单位。注意一个沙箱*内部*的容器共享它们全部，这是正确的而不是一个问题，因为消耗预算是沙箱的属性，而不是构成它的那些容器的属性。
